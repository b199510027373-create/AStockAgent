### 问题与建议

- P1 · 历史读取的 stale 判定被 now.hour>=15 门限掩盖，晨间把落后数据报成 success（open） — 建议：去掉 `and now.hour >= 15`，让历史读取与生成路径共用同一口径（落后于 last_completed_trade_date 即 stale），并在 _ledger_view docstring 写明该口径；如果确实需要保留门限，必须给出与 recommend.py:760 一致的理由并同时修改生成侧，否则两边永远互相矛盾。同时补一条用例：latest_run=_history_run(data_as_of="2026-11-05")、last_completed_trade_date=2026-11-06、now=datetime(2026,11,6,10,0)，断言 status=="stale" 且 message 含"早于最近交易日"。
- P2 · 新鲜度校验在 data_as_of 不可解析 / 日历不可用时 fail-open，页面无任何提示（open） — 建议：把"无法确认新鲜度"统一收敛成 stale 且可读：解析失败时 `stale = True`，message 写"该推荐记录 data_as_of=… 无法解析，无法确认数据新鲜度；请重新生成后再使用"；日历不可用时保留 success 但把 diagnostics["calendar_error"] 也带进 status_text 的一行提示（例如"⚠️ 交易日历不可用，未校验数据新鲜度"）。补两条用例：_history_run(data_as_of="unknown") → stale；last_completed_trade_date 抛异常 → status_text 含未校验提示。
- P2 · 跟踪 stale 的诊断把"缺沪深300 基准"说成"还没有 T+1 收盘数据"（open） — 建议：保持 stale 判定口径不变，只把 message 按原因分开：若 "T+1" 列有非空值而 "超额T+1" 全为空，写"已有 T+1 个股收益，但缺沪深300 基准数据，超额统计暂不可用；等基准数据补齐后再刷新"，并记 diagnostics["bench_missing"]=True；两者都为空时才保留现有措辞。补一条 T+1 有值、超额 NaN 的用例断言该措辞（可直接改造现有 test_no_forward_return_is_stale）。
- P2 · scheduler 向生成分支传 now 但生成侧不使用，形成"可注入时钟"的假象（open） — 建议：二选一并在 docstring 写清：(1) 删掉 scheduler.py:219 的 `now=now` 以及 use_cases._generate_view 的 now 形参（run_recommendation 的 now 文档已写明"仅历史读取"），让"生成侧不可注入时钟"成为显式事实；(2) 若希望可注入，给 recommend.generate_recommendation 增加 now 参数并用它计算 expected/generated_at/tradable_from，再由 use_cases 透传，同时在 test_hardening 里用假时钟断言 stale 分支。建议选 (1)，改动最小且不会改变生产行为。
