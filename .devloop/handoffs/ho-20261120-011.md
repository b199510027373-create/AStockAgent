### 问题与建议

- P1 · nightly 入口从未在目标 runner（windows-latest）上跑过，验收 1/5 的「干净检出可运行」只有本机脏工作区证据（open） — 建议：合并后由开发执行 `gh workflow run agent-ui-smoke.yml --ref main`（或 Actions 页面 workflow_dispatch），把 run URL、artifact 名（应含 report.json 的 8 项 PASS 与 run.json ok=true）、windows-latest 上的 Edge/Chrome 版本记入新的 developer handoff，并追加到 planItem.links.test；若首次运行失败，按 app.log/browser.log/driver.log 修脚本后重跑至绿。完成条件：handoff 里能点到一次成功的 agent-ui-smoke run，且其 report.json 含 upload/stream/steps/figure/citations/interrupt/audit/degraded 八项。在此之前 plan-20261119-001 不得置 done。
- P2 · 启动失败路径直接 return 1，跳过 run.json，与 README/workflow 承诺的「失败保留 run.json 与 report.json」不符（open） — 建议：抽出 `_write_summary(workdir, summary)`，在 `finally` 块里（或每个 return 前）统一落 run.json，并给 summary 加 `stage` 字段（"fixture" / "browser" / "driver"）区分阶段；若不希望启动失败也产出 run.json，则改为同步修订 README.md:100-103 与 workflow:6/51-52，明确「启动失败只有日志，无 run.json/report.json」。二者必须选一，且建议在 tests/test_agent_ui_smoke_contract.py 里加一条断言，防止 README 与 workflow 的路径清单再次与代码脱节。
- P2 · 降级夹具起不来时只 WARN 跳过，仍输出 SMOKE OK/ok=true，与显式 --no-degraded 无法区分（open） — 建议：默认（未传 --no-degraded）时把「降级夹具未就绪」当作失败：记录 `summary["degraded_expected"]=True`、`summary["degraded_ran"]=False` 并以非零退出码结束（或至少让 driver_exit 非 0），只有显式 --no-degraded 才允许跳过；同时让驱动在 skipped 时也往 report.json 写一条 `{"degraded": {"ok": false, "skipped": "no --degraded-url"}}`，避免「8 项」与「7 项」在证据里无法分辨。
- P2 · 注释声称「契约测试会看」图注/marker 对齐，但契约测试根本没有这条断言（open） — 建议：在 tests/test_agent_ui_smoke_contract.py 补一条断言：用 `_load(FIXTURE_APP, "agent_smoke_fixture")` 取 `FIGURE_CAPTION`/`CHART_MARKER`，再用 AST 读取 smoke_drive 模块级同名赋值（或直接用 `_load(DRIVER, "agent_smoke_drive")`，注意它 import 了 cdp 需先注入路径），assert 两者相等，并把 README.md:91 的图注字符串一起纳入比较。这样注释描述的事实才成立。
- P2 · 契约测试只查「有 upload-artifact 且路径含 report.json」，没守住 `if: always()` 与 --keep-workdir，证据上传可被静默破坏（open） — 建议：把断言补成：`assert str(uploads[0].get("if", "")).strip().lower() == "always()"`；`path = str(uploads[0].get("with", {}).get("path", ""))` 后 `assert "run.json" in path and "*.log" in path`；再 `assert any("--keep-workdir" in run for run in runs)`（runs 已在 :200 建好）。这样 upload 语义的四个关键点（存在、always、run.json+日志、保留目录）才都被守住。
- P2 · smoke_drive 的 --timeout 解析后从未使用，README 的「驱动超时（默认 300s）」对手动两步不成立（open） — 建议：二选一：(a) 删掉 smoke_drive 的 --timeout 及 run_smoke.py:354-355 的透传，README.md:63 只对 run_smoke.py 保留 `--timeout` 描述；(b) 真正实现——在 main 里 `deadline = started + args.timeout`，把每个 `_wait_text/_wait_any/cdp.wait_for` 的 timeout 改成 `min(phase_timeout, deadline - time.monotonic())`，并在超时时抛 `AssertionError("driver timeout")` 让 report.json 记下阶段。同时 README 明确写清「run_smoke 总超时 = --timeout + 120s 兜底；smoke_drive 单步超时可另由 --timeout 限定」。
