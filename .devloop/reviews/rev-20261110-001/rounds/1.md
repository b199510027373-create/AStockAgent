## 本轮问题

### P1 · 历史读取的 stale 判定被 now.hour>=15 门限掩盖，晨间把落后数据报成 success

- 位置：`astock/use_cases.py:325-338`
- 状态：未闭环
- 置信度：0.85

**证据**

_ledger_view 里 `stale = (pd.Timestamp(data_as_of) < pd.Timestamp(expected) and now.hour >= 15)`。data.py:90-93 的 last_completed_trade_date 在 15:00 前已只返回上一交易日（周一 10:00 → 周五），所以这个二次门限只会在"确实落后"时把 stale 压成 False：例如周一 10:00 打开推荐页，台账最近一批 data_as_of=周四、expected=周五 → status=success，status_text="✅ 已从 SQLite 读取 …"，没有任何落后提示。而同一条批次在生成时的诊断口径是 recommend.py:760 `stale_data = expected is not None and pd.Timestamp(data_as_of) < pd.Timestamp(expected)`（无小时门限），会显示"⚠️ 数据未更新"——生成路径与历史读取路径对同一数据给出相反结论，验收标准 4（stale 时要有明确可读诊断）在 15:00 前的窗口不成立。该分支也没有测试：tests/test_use_cases.py:218-237 只用了 now=datetime(2026,11,6,20,0)。

**建议**

去掉 `and now.hour >= 15`，让历史读取与生成路径共用同一口径（落后于 last_completed_trade_date 即 stale），并在 _ledger_view docstring 写明该口径；如果确实需要保留门限，必须给出与 recommend.py:760 一致的理由并同时修改生成侧，否则两边永远互相矛盾。同时补一条用例：latest_run=_history_run(data_as_of="2026-11-05")、last_completed_trade_date=2026-11-06、now=datetime(2026,11,6,10,0)，断言 status=="stale" 且 message 含"早于最近交易日"。

### P2 · scheduler 向生成分支传 now 但生成侧不使用，形成"可注入时钟"的假象

### P2 · 新鲜度校验在 data_as_of 不可解析 / 日历不可用时 fail-open，页面无任何提示

- 位置：`astock/use_cases.py:310-338`
- 状态：未闭环
- 置信度：0.7

**证据**

新鲜度判定在两处 fail-open：(1) use_cases.py:331-332 `except Exception: stale = False` —— data_as_of 不是可解析日期（如 "unknown"、"2026/13/40"）时直接判为新鲜，页面显示 ✅，与同函数 320-324 行"缺 data_as_of 就 stale"的规则自相矛盾；(2) use_cases.py:312-316 日历不可用时 expected=None，stale 保持 False，calendar_error 只写进 diagnostics，_render_recommendation（196-203 行）只用 message 拼 status_text，用户看到的就是一个没有前置提示的 ✅。台账是本地 SQLite/JSON，历史文件可由人工或旧版本写入，这两条都不是纯理论路径。

**建议**

把"无法确认新鲜度"统一收敛成 stale 且可读：解析失败时 `stale = True`，message 写"该推荐记录 data_as_of=… 无法解析，无法确认数据新鲜度；请重新生成后再使用"；日历不可用时保留 success 但把 diagnostics["calendar_error"] 也带进 status_text 的一行提示（例如"⚠️ 交易日历不可用，未校验数据新鲜度"）。补两条用例：_history_run(data_as_of="unknown") → stale；last_completed_trade_date 抛异常 → status_text 含未校验提示。

### P2 · 跟踪 stale 的诊断把"缺沪深300 基准"说成"还没有 T+1 收盘数据"

- 位置：`astock/use_cases.py:443-446`
- 状态：未闭环
- 置信度：0.75

**证据**

_usable_t1 只统计 `detail["超额T+1"]` 非空（use_cases.py:443-446），所以"个股 T+1 收益已有、但沪深300 基准缺失"会被判成 usable==0 → status="stale"，message 固定写成"已有 N 条推荐记录，但还没有 T+1 收盘数据"（503-508 行）。tests/test_use_cases.py:364-381 的 fixture 正是这种情况：`self._detail(excess=float("nan"))` 里 "T+1"=1.2，测试却断言消息是"还没有 T+1 收盘数据"。即使用例层保留域层 track.py:823/837-838 的 usable 口径，给用户看的这句话在有 T+1、只缺基准时是错的，而验收标准 4 要求的正是"stale 时有明确可读诊断"。

**建议**

保持 stale 判定口径不变，只把 message 按原因分开：若 "T+1" 列有非空值而 "超额T+1" 全为空，写"已有 T+1 个股收益，但缺沪深300 基准数据，超额统计暂不可用；等基准数据补齐后再刷新"，并记 diagnostics["bench_missing"]=True；两者都为空时才保留现有措辞。补一条 T+1 有值、超额 NaN 的用例断言该措辞（可直接改造现有 test_no_forward_return_is_stale）。
