## 本轮问题

### P1 · JSON 协议模式仍按原生 tool_calls/tool 线格式回放历史，非 function-calling 后端第二次请求可能 400 并静默退化为规则兜底

- 位置：`astock/agent/gateway.py:1023-1084, 354-427, 472-487`
- 状态：未闭环
- 置信度：0.72

**证据**

_complete_json（1023-1084）用 `self._invoke(first_messages, [], temperature, "json")` 把 tools 置空，但 OpenAICompatibleAdapter._payload（472-487）仍无条件 `messages=to_openai_messages(messages)`；to_openai_messages（354-427）会把会话历史里的 assistant.tool_call 还原成 `assistant.tool_calls`（伪造 call_N id）以及 `role:"tool"` + `tool_call_id` 消息。也就是说 JSON 模式第一次工具调用成功后，第二次请求的线上报文仍含 OpenAI 原生工具字段，只是不再带 tools 定义。对不支持 function calling 的后端（严格校验的 OpenAI 兼容实现、未编译 tools 模板的本地模型），这类消息可能直接 400，_invoke 抛 ChatProtocolError 后走 _fallback（1115-1148）并 degraded=True，表现为「静默降级到规则兜底」，与验收标准 ACC-02「不支持 function calling 时走 JSON 协议」不符。测试侧只覆盖了路由层：tests/test_agent_gateway.py:318-380 的 JSON 协议用例全部使用 StubModel，MockTransport 仅出现在 AdapterTests（165/193/229/282），因此没有任何用例检查 JSON 模式第二轮请求的真实请求体。

**建议**

在 JSON 协议分支把工具历史序列化为纯文本再发送：给 to_openai_messages 增加 protocol/wire 参数（或新增 to_json_protocol_messages），把 assistant.tool_call 渲染成普通 assistant 文本（如「调用工具 x，参数 {...}」）、把 tool 消息渲染成 user/system 文本「工具 x 返回：...」，确保请求体不含 `tool_calls`、`role:"tool"`、`tool_call_id`、`tools`。补一个 httpx.MockTransport 用例：JSON 模式跑两步（第一步返回工具调用、执行后第二步带工具结果），断言第二次请求 body 的 messages 无上述字段且无 tools，且流程未 degraded。修复并合入该测试后本条关闭。

### P2 · 并行 tool_calls 被静默截断为第一个，无日志/用量痕迹且无测试

- 位置：`astock/agent/gateway.py:249-251, 1221-1232`
- 状态：未闭环
- 置信度：0.8

**证据**

ChatResult.tool_call（249-251）固定 `return self.tool_calls[0]`，AgentModelAdapter.complete（1221-1232）只把 `result.tool_call` 交给 runtime，多余调用既不进 usage 记录、也不写日志、也不进入 ModelReply 的任何字段；runtime 侧每步只执行一个工具（runtime.py:185-213），因此模型一次请求多个数据点时，除第一个外全部无声丢弃，且排查时从 agent_runs/usage 里看不出发生过截断。现有测试只构造单个 tool_call（tests/test_agent_gateway.py:269 附近），无多调用用例。ADR-013 规定每步一次工具调用，但「规定」不等于「静默丢弃」，缺少可观测性会让模型反复请求同一批工具却查不出原因。

**建议**

在 AgentModelAdapter.complete（或 ChatGateway 记录处）检测 len(result.tool_calls) > 1，把「请求了 N 个工具、仅执行第一个」写入 UsageRecord 的额外字段/日志（并可给 runtime 的 observation 附加一条提示），保持执行语义不变。补一个单测：模型返回两个 tool_calls，断言只执行第一个且 usage/日志中出现截断记录。二者完成即关闭。

### P2 · config.py 新增的 AGENT_* 常量无任何引用，且与 GatewaySettings.from_env 形成两套不一致的解析规则

- 位置：`astock/config.py:42-49`
- 状态：未闭环
- 置信度：0.85

**证据**

config.py:42-49 在模块加载时读取 AGENT_PROVIDER/AGENT_MODEL/AGENT_BASE_URL/AGENT_API_KEY/AGENT_MAX_STEPS/AGENT_TOKEN_BUDGET/AGENT_TIMEOUT_SECONDS/AGENT_USAGE_LOG，但 grep 显示这些常量除定义外没有任何引用；真正生效的是 gateway.py:1273-1300 的 GatewaySettings.from_env，它重新读一遍 os.environ，并把 AGENT_USAGE_LOG 相对路径解析到 BASE_DIR。两套解析的校验也不同：config 侧只做 int/float 转换，AGENT_TIMEOUT_SECONDS<=0 也能通过，AGENT_USAGE_LOG 不做路径解析。后续维护者改 config.py 里的常量（例如调 AGENT_MAX_STEPS）不会影响网关行为，属于典型「看着像单一配置源、实际不生效」的陷阱。

**建议**

收敛为单一来源：要么 GatewaySettings.from_env 从 astock.config 读取这些常量（config 侧补 timeout>0、budget>0 校验与 usage 路径解析），要么删除 config.py:42-49 并让 .env.example 只指向网关解析。补一条测试断言 config 常量与 from_env 结果一致（若保留常量），防止再次分叉。二选一完成后关闭。
