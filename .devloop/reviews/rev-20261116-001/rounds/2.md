### P1 · 主 test job 也被绑到真实 PNG 导出：无 per-test timeout，Chrome/kaleido 抖动会拖红整个主流水线

- 位置：`.github/workflows/ci.yml:16,29-33,38,62`
- 状态：未闭环
- 置信度：0.8

**证据**

requirements.txt:7 把 kaleido==1.5.1 放进运行依赖，于是 ci.yml:38 的 `pip install -r requirements.txt` 让主 job 具备真实导出能力；ci.yml:29-33 又在主 job 装 fonts-noto-cjk；ci.yml:62 `coverage run -m pytest tests -q` 无 -m/-k/--deselect、也无 --timeout，会收集并真实执行 tests/test_agent_chart_png_export.py 与 tests/test_agent_chart_png_zh.py。zh 用例用 png_mode="require"（tests/test_agent_chart_png_zh.py:88），Chrome/kaleido 不可用时直接抛 PNGExportError 让主 job 变红；Chrome 卡死时没有 per-test 超时，只能等 ci.yml:16 的 `timeout-minutes: 15` 把整个 job 杀掉，主 job 的全部测试与覆盖率门禁一起丢失。docs/AStockAgent_png_export_ops.md:117-118 也自认「主 job…PNG 用例此时也会真实执行」。验收第 4 条要求「失败/超时可观测，不拖垮主测试流水线」，当前实现只做到了「新增独立 job」，没有做到解耦：ubuntu-latest 镜像换代、Chrome 升级或 kaleido 抖动都会同时打掉主 job。

**建议**

把真实导出彻底隔离到一个 job：1) 给两个 PNG 模块加 `pytestmark = pytest.mark.png`（或在 pytest.ini/pyproject 注册 marker）；2) 主 job 改成 `coverage run -m pytest tests -q -m "not png"`（或 `--deselect tests/test_agent_chart_png_export.py --deselect tests/test_agent_chart_png_zh.py`），并删掉主 job 的 fonts-noto-cjk 安装步骤（省 ~30s，字体只在 png-export 需要）；3) png-export job 用 `-m png --timeout=180` 保持现状。改完在 PR 贴一次新的 CI run：test job 不再依赖 Chrome、png-export 仍绿；同步更新 docs/AStockAgent_png_export_ops.md:117-118 的「主 job 也真实执行」表述。

### P2 · require 失败时「run 记 failed」只对新建 run 生效：已有 run_id 因 ON CONFLICT DO NOTHING 不会被改成 failed

- 位置：`astock/agent/chart_render.py:1437-1450`
- 状态：未闭环
- 置信度：0.75

**证据**

chart_render.py:1437-1450 在 png_mode="require" 失败时调用 `ensure_run(..., status="failed")` 后抛 PNGExportError，但 store.ensure_run（astock/agent/store.py:175-181）是 `INSERT ... ON CONFLICT(run_id) DO NOTHING`：若该 run_id 已存在（Agent 循环预建 run、或同一 run 下第二次渲染），status 保持原值（running/success），与 docs/AStockAgent_png_export_ops.md:84 写的「agent_runs.status=failed」不一致。现有用例 tests/test_agent_chart_render.py:395-420 只覆盖新 run_id，所以没暴露。

**建议**

require 失败分支在 ensure_run 之后显式落状态，例如新增 `store.fail_run(conn, run_key, reason=...)`（`UPDATE agent_runs SET status='failed', finished_at=? WHERE run_id=?`），或给 ensure_run 增加 `force_status: bool = False` 参数；补一条测试：先 `ensure_run(conn, "run_require", status="running")` 预建 run，再触发 require 失败，断言 status 变为 failed 且 artifact 行仍为 0。若产品上不希望把预建 run 置 failed，则改 ops 文档与 docstring，不要宣称「run 记 failed」。

### P2 · 复用旧 PNG 时 meta 留下矛盾的 provenance：degraded=False + 旧 png_path，却保留本次的 png_mode/png_error

- 位置：`astock/agent/store.py:255-288`
- 状态：未闭环
- 置信度：0.7

**证据**

_merge_artifact_meta（store.py:255-288）在最新一次渲染没出 PNG 时恢复旧 `png_path`、把 `degraded` 置回 False、并过滤 PNG 降级告警，但 chart_render.py:1514-1515 仍把本次的 `png_mode`/`png_error` 写进 meta，且 `png_error` 不在恢复/清理列表里。结果是：同一 HTML 先成功导出 PNG，之后 Chrome 坏掉用 `png_mode="auto"` 重渲染 → meta 变成 `png_path=<旧>，png_digest=<旧>，degraded=False，png_error="Chrome executable not found"`；用 `png_mode="off"` 重渲染 → meta 是 `png_mode="off"` 却带 `png_path`。验收第 6 条要求可追溯，这种自相矛盾的记录会让排查（ops 文档 §5 字段表）读错。tests/test_agent_store.py:436-487 只覆盖 png_path/degraded/warnings，没覆盖 png_mode/png_error。

**建议**

复用旧 PNG 时显式标注来源：在 _merge_artifact_meta 里加 `merged["png_reused"] = True`，并把 `png_error` 改名/迁移为 `png_last_attempt_error`（或直接置 None，把原因保留在一个不会与 degraded=False 冲突的键里）；同时把「产出该 PNG 的模式」写成 `png_source_mode`，不要用本次的 `png_mode` 冒充。补一条 store 级测试：先成功 PNG、再以 degraded/off 重写同一 artifact_id，断言 `png_reused=True`、`degraded=False`、`png_error` 不再表示「当前无 PNG」，且 `png_mode` 不误导。
