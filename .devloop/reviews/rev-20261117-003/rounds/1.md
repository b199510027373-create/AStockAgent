### P1 · chart_render 的 fail_run 会被 runtime 的 finish_run 以 success/partial 覆盖，审计终态与工具失败不一致

- 位置：`astock/agent/chart_render.py:1462-1469`
- 状态：未闭环
- 置信度：0.82

**证据**

png_mode=require 失败且 run_id 非空时，render 先 `store.fail_run(run_id, error=...)` 把整条 Agent run 置 failed（chart_render.py:1462-1469），再抛 PNGExportError。registry.invoke 会把工具异常转成 ToolResult(error) 而不中断 runtime（registry.py:378-388），runtime 继续执行并在结束时调用 finish_run；finish_run 无条件 UPDATE status/finished_at/completion_tokens/error（store.py:483-489），会把 failed 改回 success 或 partial。tests/test_agent_chart_render.py:398-457 只断言 fail_run 之后的即时状态，没有走 runtime 收尾，因此测不到覆盖。

**建议**

明确终态所有权：要么 chart_render 不再对整条 Agent run 调 fail_run（只记录工具错误/失败 artifact，由 runtime 统一判定），要么 finish_run 在 status='failed' 时拒绝降级/覆盖 error（例如 `WHERE status != 'failed'`，或用 `COALESCE` 保留首个失败原因）。补一个 runtime + 图表工具的集成测试：工具抛 PNGExportError 后，agent_runs.status 必须仍为 failed 且 error 非空。

### P1 · chart_render 仍把 5000 行 data 快照写进 meta_json 且不写 data_digest，真实 artifact 的 recomputed 回放不可用

- 位置：`astock/agent/chart_render.py:1535, 1207-1234`
- 状态：未闭环
- 置信度：0.86

**证据**

render 的 meta 里仍是 `"data": snapshot`（chart_render.py:1535），data_snapshot 只返回 fields/rows/row_count/truncated（chart_render.py:1207-1234），没有 data_digest。store.load_artifact 的 recomputed 分支只读 `record.meta.get("data_digest")`，缺失就抛 ArtifactReplayUnavailable（store.py:936-939）。因此对真实 render 产物调用 `load_artifact(..., mode="recomputed")` 必然失败；只有 tests/test_agent_store.py:429-438 用手工 meta `{"data_digest": "sha256:abc"}` 的合成记录能通过。spec §3.7/§4.6/§4.7 要求 data 快照落独立 blob（data.parquet/data.json），meta_json 只存 data_digest/data_rows/data_truncated；当前做法还让每个版本行携带最多 5000 行数据，agent_artifact_versions 会随版本迅速膨胀。

**建议**

渲染时计算快照的规范 digest（如 sha256(canonical_json(snapshot))），把 data_digest、data_rows、data_truncated 写进 meta，把 rows 落到独立文件（按 spec 的 data.parquet 或现有 blob 布局），并让 `_load_artifact_frame` 与 `load_artifact(mode="recomputed")` 都从该文件读取。补端到端测试：真实 render 后 meta 不含完整 rows，`load_artifact(mode="recomputed")` 能返回快照，回放图与首次渲染的 data_as_of 一致。

### P1 · _finish_audit 把 record_step 与 finish_run 放在同一个吞异常的 try 里，任一步失败都会留下永久 running

- 位置：`astock/agent/runtime.py:511-545`
- 状态：未闭环
- 置信度：0.9

**证据**

_finish_audit 在同一个 try 中先循环 record_step（runtime.py:512-524），再写 final step（526-533），最后 finish_run（534-541），异常统一被 `except Exception: pass` 吞掉（542-543），finally 只 close。若任一 record_step 抛错（例如 sqlite busy/磁盘满/约束错误），后面的 finish_run 根本不会执行；若 finish_run 自身抛错，也没有兜底。结果是 run 永久停在 running，直接违反 spec §7.2“禁止永久 running”和 AC5/审计真实性要求。当前测试只覆盖成功与非法参数，没有注入落库失败。

**建议**

把 finish_run 放进独立的 finally（或至少在外层 finally 中兜底），确保无论 step 写入是否成功都执行一次终态更新；若 finish_run 也失败，用最小 UPDATE 将 status 置 failed 并写 error，或记录可重试的审计失败标记。不要用单个 `except: pass` 包住终态写入。补测试：monkeypatch record_step 抛异常，断言 run 最终不是 running；monkeypatch finish_run 抛异常，断言有失败兜底且异常不影响 Agent 返回。

### P1 · artifact_id 仍由 digest+文件名派生，环境变化会撞身份、同内容不同文件名会重复建行

- 位置：`astock/agent/store.py:312-316, 711-719`
- 状态：未闭环
- 置信度：0.9

**证据**

artifact_id_for 的种子是 `f"{bare}\x00{filename}"`（store.py:315），chart_render.py:1423 固定传 "chart.html"，而 env_fingerprint 在 chart_render.py:1454 才计算、没有进入 artifact_id。record_artifact 在已存在分支发现 env_fingerprint 不同就直接抛 ArtifactIdentityConflict（store.py:711-719）。因此 code_version 或 plotly 升级后若 HTML 字节相同，渲染会硬失败；同一内容换一个文件名则会生成第二个 artifact 行，违反 AC2 的“内容寻址、digest 去重”和 ADR-017 C3 的“同 digest 复用目录并只插一行”。spec §4.4 规定的 id 种子是 canonical_spec+data_digest+env_fingerprint，当前实现两者都不符。tests/test_agent_store.py:299-326 只覆盖同 filename、同 env 的重复写入，未覆盖 env 变化或文件名变化。

**建议**

把 artifact 身份改为内容+环境寻址：至少将 env_fingerprint 纳入 artifact_id 种子，并按 spec §4.4 使用 canonical_spec+data_digest+env_fingerprint；文件名只作为落盘路径的一部分，不参与逻辑身份。若同一 digest 已存在但 env 不同，应生成新 artifact（新 id/新路径），而不是抛 ArtifactIdentityConflict。补两个测试：同一 HTML 在 env1→env2 下渲染得到两个 artifact 且都可用；同 digest 不同 filename 只保留一行 artifact、link 指向同一行。

### P2 · runtime 把总 token 作为 completion_tokens 传入 finish_run，prompt_tokens 永远为 0，成本拆分失真

- 位置：`astock/agent/runtime.py:534-540`
- 状态：未闭环
- 置信度：0.8

**证据**

### P2 · 迁移备份先 checkpoint 但吞掉失败，再用 shutil.copy2 复制主文件，WAL 未落盘时备份可能缺已提交事务

- 位置：`astock/agent/store.py:1250-1259`
- 状态：未闭环
- 置信度：0.78

**证据**

_backup_database 先执行 `PRAGMA wal_checkpoint(TRUNCATE)`，但用 `contextlib.suppress(sqlite3.DatabaseError)` 吞掉失败，然后直接 `shutil.copy2(db_path, backup)`（store.py:1250-1259）。WAL 模式下如果 checkpoint 因其他连接/忙而失败，主文件不包含最新已提交事务，备份就是旧快照；迁移后又 DROP 旧表，若之后需要回滚/人工恢复，备份缺少最近数据。spec §8.1 要求先 checkpoint 再备份，但没有说可以忽略 checkpoint 失败。

**建议**

检查 `PRAGMA wal_checkpoint(TRUNCATE)` 的返回（busy/log/checkpointed 列），非 0 时中止迁移并提示先停写；或直接使用 sqlite3 的 `conn.backup()` / `VACUUM INTO` 生成一致性备份，不依赖主文件复制。备份完成后再校验备份的 integrity_check 和关键表行数。补一个 WAL 未 checkpoint 场景的测试（可用第二个连接持有读事务模拟 busy）。
